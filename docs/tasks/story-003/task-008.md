## 🪜 Les étapes

### Étape 1 : Écris la documentation

**Où :** la racine du projet

**Action :**

> Crée `docs/tooling/sonarqube.md` (réponds **Cancel** à IntelliJ) avec ce contenu. Il est déjà en
> anglais : relis-le et adapte les tournures si tu le souhaites, sans changer les valeurs.
>
> ```markdown
> # SonarQube Configuration
>
> SonarQube is configured in its web UI: this configuration is not stored in any file of the
> repository. This page describes how to redo it on a fresh SonarQube instance.
>
> ## 1. Admin password
>
> 1. Log in at `http://localhost:9000` with the default `admin` / `admin`.
> 2. SonarQube forces a password change: use a password generated by a password manager.
> 3. Check that the default credentials are refused:
>    `curl -s -u admin:admin http://localhost:9000/api/authentication/validate` returns `{"valid":false}`.
>
> ## 2. Project
>
> | Field | Value |
> |-------|-------|
> | Project display name | `Step by Step` |
> | Project key | `step-by-step` |
> | Main branch name | `main` |
>
> The analysis itself is configured in the `pom.xml` (Maven scanner), not in a
> `sonar-project.properties` file.
>
> ## 3. Quality Gate
>
> `step-by-step-gate` is a copy of the built-in *Sonar way* gate, with one change: coverage on new
> code must be at least **60%** (instead of 80%), as decided in the specification. It is assigned to
> the `step-by-step` project.
>
> ## 4. Tokens
>
> | Token | Type | Stored in | Used by |
> |-------|------|-----------|---------|
> | `jenkins-step-by-step` | Project Analysis Token (`step-by-step` only) | Jenkins credential `sonar-token` (Secret text) | the pipeline (story 013) |
> | `scripts-tp` | User Token | password manager | `scripts/check-sonarqube.sh` |
>
> Load the user token in the terminal without displaying it or keeping it in the history:
>
> ```bash
> read -rs SONAR_TOKEN && export SONAR_TOKEN
> ```
>
> ## 5. Verification
>
> ```bash
> ./scripts/check-sonarqube.sh
> ```
>
> The script checks token authentication, that `admin/admin` is refused, that the project exists,
> that it uses `step-by-step-gate`, and that the coverage threshold is 60%. It displays
> "SonarQube is compliant" and exits with code 0; it exits with code 1 immediately if the token is
> refused, or after all checks if any other check fails.
> ```

**✅ Vérifie que :**
- [ ] Le fichier est dans `docs/tooling/`
- [ ] Aucune **valeur** de jeton ni de mot de passe

---

### Étape 2 : Cherche le jeton utilisateur dans les fichiers

**Où :** la racine du projet

**Action :**

> ```bash
> echo "${#SONAR_TOKEN}"
> grep -rlF "$SONAR_TOKEN" . --exclude-dir=.git || echo "OK : jeton absent des fichiers"
> ```

**Résultat attendu :** `44`, puis `OK : jeton absent des fichiers`.

**Pourquoi afficher la longueur d'abord ?** Si `SONAR_TOKEN` était vide, `grep` ne chercherait rien
et afficherait quand même `OK`. La longueur prouve que la recherche a un sens.

---

### Étape 3 : Cherche un jeton d'analyse oublié

**Où :** la racine du projet

**Action :**

> Le jeton d'analyse n'est pas dans ton terminal, mais tous commencent par `sqp_` (et les jetons
> utilisateur par `squ_`). Exécute :
>
> ```bash
> grep -rlE 'sq[pu]_[0-9a-f]{40}' . --exclude-dir=.git || echo "OK : aucun jeton SonarQube"
> ```

**Résultat attendu :** `OK : aucun jeton SonarQube`

**Pourquoi chercher un motif ?** On ne connaît pas la valeur du jeton d'analyse (elle n'est que dans
Jenkins), mais on connaît sa **forme**. Le motif ne peut pas correspondre aux exemples de cette doc :
`sqp_…` n'est pas suivi de 40 caractères hexadécimaux.

**Où :** la racine du projet

**Résultat attendu :** la même liste qu'à la fin de la story 002 : `scripts/` et `docs/` étaient déjà

| Problème | Solution |
|----------|----------|
